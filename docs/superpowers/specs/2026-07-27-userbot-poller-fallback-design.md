# Поллер-фоллбэк для userbot: получение постов через историю канала

Дата: 2026-07-27
Статус: утверждён, готов к реализации

## Проблема

Userbot (pyrogram) получает посты мониторинг-каналов через push-апдейты. Для 22 из 37
каналов эти апдейты не приходят вообще: за две недели ноль событий `Получено сообщение`
по этим `chat_id`, при том что каналы активны и постят.

Что проверено и исключено:

- Аккаунт подписан на каналы, владелец видит свежие посты в официальном приложении.
- Переподписка через панель (реальный `leave` + `join`) не помогла: 10 часов тишины
  при новых постах в канале.
- Перезапуск процесса не помог: состав молчащих каналов не изменился.
- Настройки в БД корректны: каналы привязаны к центральным чатам, ключи на месте.
- Отправка исправна: 127 отправок за две недели, ноль ошибок.

Что работает: **чтение истории тех же каналов той же сессией**. Команда `/check`
(`get_chat_history`) успешно собрала по 25 сообщений с четырёх молчащих каналов —
`@gorilla_crypto`, `@crypto_musk1`, `@techcryptoanalyst`, `@theanalystcrypto`,
`@cobratradinggroup`.

Вывод: сломана доставка апдейтов конкретной сессии, а не доступ к каналам.

## Решение

Добавить поллер: периодически запрашивать историю каждого мониторинг-канала через
`get_chat_history` и отдавать новые сообщения в существующий обработчик. Push остаётся
как быстрый путь, поллер работает параллельно и подбирает всё, что push не принёс.

Поллер не лечит причину, а обходит сломанное звено. Это осознанный выбор: причина лежит
на стороне Telegram и нам недоступна, а чтение истории подтверждено на практике.

## Границы

Входит в объём:

- Опрос всех мониторинг-каналов из БД (`is_central = 0`).
- Хранение позиции чтения по каждому каналу.
- Защита от повторной отправки при рестарте.
- Защита от рассылки старых постов при первом запуске.
- Пейсинг и обработка `FloodWait`.
- Однократная отправка альбомов (медиа-групп).

Не входит:

- Логика фильтрации и маршрутизации (ключи, стоп-слова, привязки) — не меняется.
- X-скраппер — не затрагивается.
- Поведение push-обработки — не меняется.
- Мульти-аккаунт для userbot.

## Архитектура

Поллер — асинхронная задача внутри процесса `bot`, использующая уже залогиненный
клиент `userbot_manager.client`. Отдельный процесс не подходит: вторая pyrogram-сессия
на том же аккаунте конкурирует за session-файл.

Компоненты:

1. `app/userbot/poller.py` — цикл опроса.
2. `app/userbot/poller_state.py` — позиции чтения и отметки обработанных сообщений в Redis.
3. Точка запуска: `asyncio.gather` в `app/__main__.py`, рядом с `userbot_manager.start()`
   и `run_bot()`.
4. Настройки в `settings.json` рядом с `scrapper_page_sleep_sec`.

## Поток данных

```
таймер (интервал N сек)
  → ChatRepo.get_monitoring_chats()
  → для каждого канала:
      get_chat_history(chat_id, limit)     # свежие первыми
      → набрать сообщения новее last_id
      → развернуть в хронологический порядок
      → для каждого: Handlers.message_handler(client, message)
      → записать новый last_id
      → пауза между каналами
```

Обработчик дальше работает без изменений: проверка чата в БД, привязка к центральному
чату, ключи (гибридная логика), стоп-слова, отправка.

## Хранение состояния

Redis, две группы ключей:

| Ключ | Значение | TTL | Назначение |
|---|---|---|---|
| `poller:last_id:{chat_id}` | id последнего обработанного сообщения | нет | позиция чтения по каналу |
| `poller:seen:{chat_id}:{message_id}` | `1` | 48 ч | отметка «сообщение уже обработано» |
| `poller:group:{chat_id}:{media_group_id}` | `1` | 48 ч | отметка «альбом уже отправлен» |

Префикс `poller:` выбран так, чтобы существующая чистка Redis не задела эти ключи:
`cleanup_old_posts` удаляет только ключи по шаблону `post:*`.

Отметка `seen` заменяет собой кэш в памяти `Handlers._processed_messages`, который
теряется при рестарте. Кэш в памяти остаётся как быстрая проверка перед обращением
к Redis.

## Ключевые требования

### Bootstrap: первый запуск не должен рассылать старые посты

Если по каналу позиции ещё нет, поллер запрашивает последнее сообщение, записывает его
id как `last_id` и **не передаёт его в обработчик**. Без этого первый же запуск выльет
десятки старых постов в боевые чаты.

### Дедупликация должна переживать рестарт

Перед обработкой сообщения проверяется `poller:seen:{chat_id}:{message_id}`. Отметка
ставится в обработчике, поэтому покрывает оба пути — и push, и поллер. Это же снимает
риск двойной отправки, когда push и поллер видят одно сообщение.

### Позиция и push не связаны

Push-доставка не двигает `last_id`. Поллер всегда идёт от своей позиции, а повторы
отсекаются отметкой `seen`. Так пропуски в push (наш случай) не приводят к потере
сообщений.

### Пейсинг

Пауза между каналами (по умолчанию 2 секунды). При `FloodWait` — ожидание `ex.value`
секунд, затем продолжение со следующего канала. Ошибка по одному каналу
(`PeerIdInvalid` у приватных, недоступность) логируется и не прерывает цикл.

### Альбомы отправляются один раз

Сообщения одной медиа-группы приходят по одному, каждое сейчас запускает отправку
альбома. Перед отправкой проверяется и ставится отметка `poller:group:{chat_id}:{media_group_id}`.

## Настройки

В `settings.json` (значения по умолчанию в `default_data`):

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `poller_enabled` | `true` | включение поллера |
| `poller_interval_sec` | `300` | интервал между полными обходами |
| `poller_limit` | `50` | максимум сообщений за одну выборку по каналу |

Если новых сообщений оказалось больше лимита, обрабатываются самые свежие из выбранных,
позиция сдвигается на максимальный обработанный id, а в лог пишется предупреждение с числом
пропущенных. Это осознанный размен: догонять длинную историю канала опаснее для лимитов,
чем потерять часть постов за редкий всплеск активности.
| `poller_channel_delay_sec` | `2` | пауза между каналами |

Геттеры добавляются в класс `Settings` по образцу `get_scrapper_page_sleep_sec`.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| `FloodWait` | ждём `ex.value` секунд, продолжаем |
| `PeerIdInvalid`, канал недоступен | лог `warning`, переходим к следующему каналу |
| Redis недоступен | лог `error`, итерация пропускается; отправок вслепую нет |
| Исключение в обработчике сообщения | лог `error`, продолжаем со следующим сообщением |
| Клиент userbot не запущен | ждём следующей итерации |

Цикл поллера не должен падать целиком ни при какой ошибке отдельного канала.

## Логирование

Формат сообщений — как в остальном проекте (loguru, русский текст):

- начало обхода и число каналов;
- по каналу: сколько новых сообщений найдено, если больше нуля;
- bootstrap: «канал X: первая инициализация, стартовая позиция N, сообщения не отправляем»;
- пропуск по `seen`;
- ошибки по каналу.

Логи должны позволять ответить на вопрос «дошёл ли пост канала X до обработки» тем же
способом, что и сейчас — поиском по `chat_id`.

## Тестирование

Юнит-тесты на изолированной логике, без реального Telegram и Redis:

1. Bootstrap: пустая позиция → позиция записана, обработчик не вызван.
2. Обычный проход: три новых сообщения → обработчик вызван трижды в хронологическом
   порядке, позиция обновлена на максимальный id.
3. Повтор: сообщение с отметкой `seen` → обработчик не вызван.
4. Альбом: три сообщения с одним `media_group_id` → отправка одна.
5. `FloodWait` по каналу → цикл не падает, следующий канал обрабатывается.

Зависимости (клиент, Redis, репозиторий чатов) подменяются фейками.

## Проверка на проде

После выката:

1. В логах появляются строки обхода и bootstrap по каждому каналу; отправок в первые
   минуты нет.
2. Через один-два интервала: сообщения от ранее молчавших каналов доходят до обработчика —
   `grep -c "chat_id=-1001297561296" bot.log` растёт.
3. Отсутствие дублей: посты живых каналов (MACD) не задваиваются в центральных чатах.
4. Перезапуск процесса не приводит к повторной рассылке.

## Риски

| Риск | Смягчение |
|---|---|
| Первый запуск разошлёт старые посты | bootstrap-логика, проверяется тестом |
| Рестарт вызовет повторы | отметки `seen` в Redis с TTL 48 ч |
| Флуд-лимиты Telegram | пауза между каналами, обработка `FloodWait`, интервал 5 минут |
| Приватные каналы недоступны для чтения истории | ошибка логируется, канал пропускается; список таких каналов виден в логах |
| Задержка доставки до интервала опроса | приемлемо; push продолжает работать там, где работает |
